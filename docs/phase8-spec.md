# Phase 8 実装仕様 — ヘクスグリッドの日本地図

企画書 `docs/design.md` §3 の

> 正式版では都道府県、都市、工業地帯、港湾、鉄道路線などをより詳細に表現する

を、都道府県より細かい単位で実現する。

## 0. 方針

### なぜ作り直すか

現在の `scenarios/japan47.json` は 1 都道府県 = 1 ノード。これでは

- 県内の地形差が消える（静岡が海岸線と南アルプスを一つの地形で代表する）
- 県内のチョークポイント（碓氷峠のような隘路）を表現できない
- 東京が 1 ノードなので首都圏の内部で戦線が動かない
- 部隊が県を丸ごと占めるため前線が粗い

### 地形を推測で置かない

**これが最重要の制約。** 200 を超えるマスに人間の記憶で山地・平野を割り振れば、
それらしいが実際とは違う地図になる。地形は**実データから導出する**。

国土地理院の標高タイルが利用できることを確認済み。

```
https://cyberjapandata.gsi.go.jp/xyz/dem_png/{z}/{x}/{y}.png
RGB → 標高(m) = (R*65536 + G*256 + B) * 0.01   （2^23 以上は負値）
海域は (128, 0, 0)
```

z=8 のタイル 1 枚で 256×256 画素、日本全域を数十枚で覆える。
デコードと標高の妥当性は検証済み（中部山岳のタイルで最大 3096m）。

### 生成物はデータ

マップは `scenarios/*.json` であり、生成スクリプトは Rust のビルドに含めない。
`crates/sim` の外部依存 0 は維持する。スクリプトは `tools/` に置き、
Python + numpy + Pillow でよい（`python/requirements-dev.txt` とは別管理）。

**生成結果をリポジトリにコミットする。** 実行のたびにネットワークを叩かない。

## 1. マス割り

### ヘクスグリッド

日本列島を覆う一定間隔のヘクスグリッドを敷く。

- **辺間隔 40km** を既定とする（陸地マス数の目標 250〜300）
- 投影は簡易でよい。緯度経度を等距離円筒に近似し、
  日本の緯度帯（北緯 24〜46 度）で経度方向を `cos(lat)` 補正する
- 中心が陸地（標高タイルが海域でない）のヘクスを採用する
- 陸地画素の割合が閾値未満のヘクスは捨てる（小島の取りこぼしは許容する）

### 地形の決定

各ヘクスに含まれる標高画素から決める。**閾値は `tools/` 内の定数にまとめる。**

| 条件 | 地形 |
|---|---|
| 標高中央値が高い | `Mountain` |
| 標高中央値が中程度、または起伏が大きい | `Hill` |
| 標高中央値が低く起伏も小さい | `Plain` |
| 上記のうち人口密度が突出して高いもの | `Urban` |

起伏は同一ヘクス内の標高の分散か、上位・下位分位差で測る。
**単純な平均標高だけで決めない。** 甲府盆地のように、
周囲が山でも底は平地であるような場所を潰さないため。

### 隣接

- ヘクスの幾何的な隣接（最大 6 方向）で、双方が陸地なら陸路で結ぶ
- リンク種別は両端の地形から決める。平地同士は `Rail`、
  山地が絡めば `Road`、標高差が大きければ `Road`
- **島嶼間は海峡リンクで結ぶ。** 陸路の連結成分を求め、
  成分間を最短の海上距離で接続する。接続する海上距離に上限を設け、
  それを超える成分は孤立を許す（離島）

### 保たねばならないチョークポイント

Phase 2 の設計意図（企画書 §8）を新しい地図でも維持する。

- **関門**（本州—九州）は `Tunnel`。制海権の影響を受けない唯一の陸路であり、
  海上封鎖に対する九州の価値を決めている
- **青函**（本州—北海道）は `Strait`
- **瀬戸内**（本州—四国）は `Strait`
- **中央高地**は山地ヘクスの連なりとして自然に生じるはず。
  生じない場合は地形判定の閾値を見直す（配置を手で捻じ曲げない）

## 2. 人口と生産能力

### 人口

都道府県別の人口（万人）を既知の表として持ち、各県のヘクスへ配分する。

- 配分の重みは**低標高かつ起伏の小さい面積**とする。
  日本の人口は平野に集中しており、面積按分より実態に近い
- ヘクスがどの県に属するかは、県庁所在地の緯度経度からの最近傍で決める。
  県庁所在地 47 点の座標は表として持つ（検証可能な既知の値）

### 生産能力

`Good` 6 品目の能力を人口と地形から導出する。

| 品目 | 導出 |
|---|---|
| `Food` | 平地面積に比例。山地はごく小さい |
| `Energy` | 人口と面積に薄く比例（全国に分散） |
| `Steel` | 人口と、沿岸・平地であることに比例（臨海工業地帯） |
| `Machinery` | 人口密度に強く比例（都市圏に集中） |
| `Munitions` | 人口に比例 |
| `Arms` | 人口密度に比例、`Machinery` より集中 |

**合計値の目標を先に決め、それに合わせて係数を較正する。**
現在の `japan47.json` の全国合計は 6 勢力を支えられていない
（全勢力が `munitions=0` / `steel=0` / `energy≈0` で戦争が起きない）。
新しい地図では、**全勢力が軍需品を継続的に生産できること**を
受け入れ基準に含める。

### 港湾

海に接するヘクスに港を与える。規模は接する海岸線の長さと人口による。

## 3. 勢力と海域

- 勢力は地域ブロック単位。数は 6〜8。ヘクスを地方（北海道・東北・関東・
  中部・近畿・中国・四国・九州）で束ねる
- 海域は 8 前後。沿岸ヘクスを面する海域に割り当てる
- 初期外交と勝利条件はシナリオ宣言制（既存の仕組み）。
  japan47 と同じ形式で書く

## 4. 検証

### 生成物の検証

既存の `Scenario::validate` を通すこと。加えて生成スクリプト側で:

- 陸路の連結成分が意図した数であること（本州・北海道・四国・九州・沖縄）
- 関門・青函・瀬戸内のリンクが存在し、種別が正しいこと
- 各県の人口配分の合計が元の県人口に一致すること
- 地形の分布が妥当であること（山地が過半を占めるなど極端でないこと）

### シミュレーションの検証

**地図として正しいだけでは足りない。遊べることを確認する。**

- 720 日を完走し、同 seed で `--json` がバイト一致すること
- **全勢力が軍需品を継続的に生産していること**（`munitions > 0` が保たれる）
- **戦闘が実際に起きていること。** japan47 は 720 日で陸戦 5 回、
  部隊数が 620 日間不変という「戦争が起きていない」状態だった。
  新しい地図では戦闘回数と部隊数の推移を報告し、
  戦争が成立していることを数値で示すこと
- `--bench` で性能を測り、47 県マップとの比を報告すること。
  Stage 6C の実測では AI の判断コストが地域数より速く増えており、
  ここが最大の性能リスクである

### 既存資産の維持

- `scenarios/mvp.json` の seed 1 / 720 日のハッシュ
  `0138bf5d537417128e737d3fb68ff55591b8c5dc96e7f382cedaec3b63ffb714` は不変
- `scenarios/japan47.json` は残す（比較対象・回帰テストとして有用）
- 観測ベクトルの長さは `GET /schema` から取れるため Python 側は無変更で追随するはず。
  実際に確認すること

## 5. 段階

| stage | 内容 |
|---|---|
| 8A | 標高データの取得とヘクス生成、地形判定。地図として妥当か検証 |
| 8B | 人口・生産能力・港湾・勢力・海域を載せ、遊べる状態にする |
| 8C | 性能と AI の破綻に対処する（8B の測定結果を見て決める） |

8A で「地図として正しいか」を、8B で「ゲームとして成立するか」を、
別々に検証する。混ぜると原因の切り分けができない。

## 共通の制約

`docs/conventions.md` に従う。特に:

- `crates/sim` は外部クレート依存 0、Bevy 非依存、完全決定論
- フォールバック禁止。データが欠けたら失敗する
- テストは落ちうることを確認してから信用する
- 検証は実際の使用条件で行う。画面は見る、数えない
