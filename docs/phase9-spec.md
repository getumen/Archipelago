# Phase 9 実装仕様 — 輸送網の独立レイヤー化

企画書 `docs/design.md` §3 / §8 / §21-2 を実装する。
`docs/future-work.md` の「輸送網を独立レイヤーにする（案 B）」の着手。

## 0. なぜやるか

### 今の補給が計算しているもの

`logistics::recompute_supply` は各地域について

    supply[j] = max over 経路 ( min over 経路上のリンク ( 通過量 ) )

を求めている。**最良経路のボトルネック値**であり、到達可能性の指標である。

ここに決定的な性質がある。**リンクの容量は消費されない。**

```
1 本の鉄道の後ろに 1 個師団   → 補給 = ボトルネック値
1 本の鉄道の後ろに 10 個師団  → 補給 = 同じボトルネック値
```

同じ路線を使う 2 つの戦線が競合しない。地域の中では部隊が備蓄を奪い合うが
（`distribute_supply`）、**輸送網そのものは奪い合いにならない。**

結果として、兵を集めることに兵站上の代償が存在しない。「どこに何個師団置くか」
という判断から兵站の要素が丸ごと抜けている。

### 何が得られるか

1. **輸送量が有限になる。** 集中に代償が生まれ、分散する理由ができる
2. **経路が存在する。** 今はエンジンにもプレイヤーにも「経路」という概念がない。
   §21-2 の物流中心の戦争は、「どの路線を断つか」が直接の意思決定になって
   初めて成立する
3. **地域以外の攻撃目標ができる。** 今、補給を叩く手段は地域の占領か制海権だけ。
   地域数を増やさずに遮断の解像度が上がる

### 案 A（地域を刻む）との関係

`future-work.md` の案 A・案 B の比較は japan47（47 ノード）時代の記述であり、
**現状と食い違っている。** japan_hex で 289 マスになり、案 A は事実上済んだ。

しかし刻んでもモデルは変わっていない。依然としてボトルネック到達可能性である。
**案 B の利益は刻んだこととは無関係にそっくり残っている。**
着手にあたり `future-work.md` の当該節を現状に合わせて書き直すこと。

## 1. 層の分離

**これが Phase 9 の骨子である。**

| 層 | 単位 | 何に使うか |
|---|---|---|
| 地域 | `Region` | 政治・経済・人口・生産。**変えない** |
| 地域リンク | `Region::links` | **部隊の移動のみ。** 補給には使わない |
| 輸送網 | 新規 | **補給の輸送のみ。** 路線・ジャンクション・港 |

地域は政治と経済の単位のまま残す。補給は地域リンクを辿るのをやめ、
輸送網の上を流れる。企画書 §8 の

> 工場・倉庫・港 → 鉄道 → 補給拠点 → 前線部隊

がそのまま構造になる。

### 輸送ノード

```
Junction   路線の分岐点。地域に属する
Depot      補給拠点。地域に属し、その地域の部隊へ払い出す
Port       港。地域に属し、海域に面する。封鎖の対象
```

各ノードは所属地域を持つ。1 つの地域が複数のノードを持ってよく、
ノードを 1 つも持たない地域があってよい（そこへは補給が届かない）。

### 輸送路線

```
TransportLine { from: NodeId, to: NodeId, kind, capacity, condition }
```

- `kind` は `Rail` / `Road` / `Sea`（港と港を海域経由で結ぶ）
- `capacity` は 1 tick に通せる量の上限
- `condition` は 0〜1 の健全度。戦災・遮断で下がり、**回復経路を持つ**

### 港の扱い

現在 `Region::port` は地域の属性である。輸送網では港はノードになる。
`naval::is_port_blockaded` は**地域ではなくノードを封鎖する**。

`Region::port` を削除するか残すかは実装時に決めてよいが、
**同じ事実が 2 か所に別々に存在する状態は作らない。**

## 2. 補給を有限流量にする

### 計算するもの

各勢力について、供給源から需要点へ、**容量に制約された流量**を求める。

```
供給   各ノードの属する地域の生産（+ 港からの輸入）
需要   各 Depot が担当する地域にいる自勢力部隊の必要量
制約   各路線の capacity * condition を超えて流せない
```

`world.supply[region]` は「その地域が引ける上限」から
**「その地域へ実際に流れた量」**に意味が変わる。

### 配分の規則

**規約 §6 と CLAUDE.md の「繰り返し踏んだ欠陥」がそのまま効く。**

- **固定の優先順位を置かない。** 路線が過需要なら、需要に比例して按分する。
  どの戦線が先に取るかを順序で決めてはならない
- **1 tick の容量は減る予算として持つ。** 残量に比率を掛け直す実装にしない。
  RL エージェントが行動を連打する前提である
- **`condition` に回復経路を持たせる。** 下がりっぱなしにしない
- **発令時点の値を焼き込まない。** 経路を一度決めて保持せず、現在の状態から
  毎 tick 求める

### 決定論

- 路線とノードの反復順を固定する。`HashMap` / `HashSet` の順に依存しない
- 浮動小数の加算順序を固定する
- 反復解法を使う場合、**打ち切り条件を反復回数で固定する。**
  収束判定を浮動小数の比較で行うと、最後の 1 回の有無が seed 間で割れる

### 何を壊すか

補給モデルの変更は**全シナリオの結果を変える。** これは想定どおりであり、
欠陥ではない。ただし次は維持する。

- 同一 seed で 2 回実行して一致する（`determinism` テスト）
- API 経由と headless が一致する
- `--agent llm --backend fail` と `--agent heuristic` が一致する
- `--newspaper` の有無で結果が変わらない

## 3. データ

### すべてのシナリオが輸送網を宣言する

**フォールバック禁止。** 輸送網のないシナリオを地域リンクで補うことはしない。
`mvp.json` / `japan47.json` / `japan_hex.json` のすべてに輸送網を持たせる。
欠けていれば `Scenario::validate` が明確に失敗する。

### japan_hex の路線は実データから導出する

Phase 8 の制約「**地形を推測で置かない**」をそのまま適用する。
200 を超えるマスに記憶で路線を引けば、それらしいが実際とは違う地図になる。

国土数値情報の鉄道データ・港湾データから導出する。
生成物は `scenarios/japan_hex.json` にコミットし、
生成スクリプトは `tools/` に置く（`crates/sim` の依存 0 は維持）。

導出後に検証する。

- 東海道・山陽が本州の主幹として通っていること
- 関門・青函・瀬戸内が輸送網でも要衝であること（Phase 2 の設計意図）
- 主要港（横浜・名古屋・神戸・北九州・苫小牧）がノードとして存在すること
- 連結成分が本州・北海道・四国・九州・沖縄に対応すること

`mvp.json` と `japan47.json` は規模が小さいので手で書いてよい。
**mvp は参照実装であり、決着する戦争が成立している状態を維持する。**

## 4. 観測・行動・AI

### 観測ベクトル

**路線ごとに出す。** 輸送網を意思決定の対象にする以上、見えなければ意味がない。

各路線について少なくとも `capacity` / `condition` / 現在の流量 /
自勢力が使えるか を出す。ノードについても封鎖・所属を出す。

観測長は伸びる。Python 側は `GET /schema` から追随するが、
**保存済みの方策は無効になる。** これは受け入れる。
`python/` のテストが新しい観測長で通ることを確認する。

### 行動

最低限、次を追加する。

- 路線の遮断・復旧に関わる行動（具体の形は実装時に決める）
- `Build` の `Project` に輸送網に対するものを追加する

**新しい行動を足すときは `Action::layer()` の網羅マッチを更新する。**
ワイルドカードがないので、足し忘れればコンパイルが止まる。

### AI

`HeuristicAgent` が輸送網を認識しない状態で出すと、AI 同士の対戦で
新しいレイヤーが実質的に無効になる。最低限、**自勢力の補給が細っている
路線を認識して優先度を上げる**程度は入れる。

補給の地図モードは既に存在する（`MapMode::Supply`）。
輸送網を**線として描く**。地域の塗りではなく路線そのものを見せる。

- 流量に応じた太さか明るさ
- 容量に対して逼迫している路線を区別する
- 遮断されている路線を区別する

**画面は見る。数えない。** japan_hex を既定ズームで撮り、
主幹が主幹に見えること、逼迫が判別できることを目で確認する。

## 7. 受け入れ基準

### Stage 9A

- `cargo build --workspace` 警告 0、`cargo test --workspace` 全通過
- `cargo tree -p archipelago-sim` が空のまま
- **既存の全テストが意味を変えずに通る。** 9A は挙動を変えない
- 3 シナリオすべてが輸送網を持ち、`validate` を通る
- 輸送網が欠けたシナリオ、存在しないノードを指す路線、
  所属地域のないノードがそれぞれ明確なエラーになる

### Stage 9B

- **同じ路線の後ろに部隊を増やすと、1 部隊あたりの補給が下がる。**
  これが Phase 9 の存在理由であり、テストで固定する
- **路線を 1 本断つと、その先の補給が落ちる。** 迂回路があれば
  迂回路の容量まで落ちる（0 になるとは限らない）
- 過需要時の配分が需要に比例している。順序に依存しない
- `condition` が回復する経路がある
- 決定論（同一 seed で一致、API と headless で一致）
- mvp が 720 日を完走し、**決着する戦争が成立したままである**

### Stage 9C

- 上記「japan_hex の路線」の検証項目をすべて満たす
- japan_hex が 720 日を完走し、戦争が成立している
  （既存の受け入れテストの閾値を維持する）
- 永久破綻がない（軍需品ゼロの連続日数が基準以下）

### Stage 9D

- 観測長が `GET /schema` から取れ、`python/` のテストが通る
- AI が輸送網を認識している（認識しない版との差を数値で示す）
- 地図で輸送網が見える。**撮って目で確認する**

### Stage 9E

- japan_hex の 720 日が許容できる時間で完走する
- `--bench` で Phase 8 との比較値を出す
